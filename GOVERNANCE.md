# Governance

## Project Maintainer

**e-Studies App** is currently maintained by **Panagiotis Bellias**.

The project maintainer is responsible for:

* Reviewing and merging pull requests
* Managing releases and versioning
* Maintaining the project's development and release processes
* Reviewing significant architectural changes
* Coordinating security responses
* Making final decisions when consensus cannot be reached

The current maintainer is also the repository's default code owner.

## Decision Making

The project aims to make decisions through open discussion and collaboration.

For normal changes:

1. Open an issue or pull request describing the proposed change.
2. Discuss the approach with the project maintainer and contributors.
3. Prefer solutions that are technically sound, maintainable, well tested, and aligned with the project's goals.
4. The maintainer makes the final decision when a decision cannot be reached through discussion.

Small bug fixes, documentation improvements, and routine maintenance can normally be handled through the standard pull request process.

Significant architectural, dependency, security, or project-direction changes should be discussed before implementation where practical.

## Code Review

Pull requests should:

* Have a clear purpose and description.
* Pass the project's automated CI checks.
* Include appropriate tests for code changes.
* Follow the project's contribution and coding guidelines.
* Receive review from the designated code owner before merging.

The repository's `CODEOWNERS` file defines the current code ownership and review responsibility.

## Issue Escalation

Issues should normally be raised through GitHub Issues.

If an issue requires additional attention:

1. Add relevant information or clarification to the existing issue.
2. Request maintainer attention in the issue if necessary.
3. For unresolved technical or project-direction questions, the maintainer provides the final decision.

Please avoid opening duplicate issues solely to escalate an existing discussion.

## Security Escalation

Security vulnerabilities must **not** be reported through public GitHub Issues.

Please follow the process described in [`SECURITY.md`](SECURITY.md), including the use of a private GitHub Security Advisory where appropriate.

Security issues take priority over normal feature requests and maintenance work.

## Code of Conduct

All project participants are expected to follow [`CODE_OF_CONDUCT.md`](CODE_OF_CONDUCT.md).

Reports concerning unacceptable behavior should be handled according to the enforcement process described in the Code of Conduct and brought to the project maintainer.

## Becoming a Maintainer

As the project grows, additional maintainers may be invited based on sustained contributions, technical knowledge, reliability, and familiarity with the project's goals and development practices.

Changes to the maintainer structure will be documented in this file.

## Governance Changes

This governance model may evolve as the project and contributor community grow.

Significant changes to governance should be documented through a pull request so that the project history remains transparent.
